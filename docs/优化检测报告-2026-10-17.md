## 一、ColorOS「卡启动页」诊断

### 结论（按可能性排序）

**附件说明**：`PJZ110_16.0.0.206.zip` 是 3.4GB 的 **ColorOS 整包 OTA 固件**（payload.bin，签名 OTA），不含应用日志，无法用于本诊断。真机日志获取方式见文末。

**第 1 可能：设备装的是 v3.2 或更早版本，命中历史 SW 缓存死锁。**
v3.3 的修复提交（`fd86ad3`）自述了完整病灶链：v3.2 及以前原生端注册 Service Worker → SW 跨 APK 版本存活并缓存入口页 → 升级后导航回落到「引用旧 assets hash 的旧入口页」→ 旧 assets 已不存在 → 404 → React 永不挂载 → **卡启动页**。
v3.3 起原生端不再注册 SW（`src/main.jsx:24-32`），v3.6.5 启动失败页还带「清除缓存并重启」自愈按钮（`index.html:115-132`，一键注销全部 SW + 清空 Cache API）。**但这套自愈代码必须先有一次成功启动才能随新版装进去——旧版本自我修复不了旧版本**。

**第 2 可能：v3.6.5 其实显示了「启动没有完成」失败页，被当作卡启动页。**
v3.6.5 启动兜底（`index.html:89-133`）：10 秒看门狗（TIMEOUT=10000）+ `window.onerror` / `unhandledrejection` 捕获 + 失败页显示**真实错误文本**。失败页不是死锁——它带「重新加载」和「清除缓存并重启」两个出口。若设备上看到的是这个页面，`boot-fail-msg` 一行就是确切病因。

**第 3 可能（对 PJZ110 可基本排除）：WebView 过旧导致 JS 崩溃。**
ColorOS 16（2026 机型）WebView 为 Chromium 130+ 级别，远高于应用所需。但该风险对**低版本设备真实存在**，见下节基线问题。

### 排查步骤（按顺序执行，5 分钟）

1. 设备上打开 **我的 → 关于/设置**，确认已装版本号。若 < v3.6.5 → 先升级再观察。
2. 若停留页面有「启动没有完成」字样 → **拍下错误文本行**（boot-fail-msg），那就是根因；先点「清除缓存并重启」。
3. 仍卡纯启动图（无任何文字）→ USB 连电脑，ColorOS 开发者选项开「USB 调试」+「USB 调试（安全设置）」，电脑 Chrome 打开 `chrome://inspect`，inspect 该 WebView 看 Console 报错。
4. 有 adb 环境时：`adb logcat -s Capacitor:V chromium:V Console:V` 复现一次启动即得完整日志。

### 基线问题（旧设备上的隐性坑，非 PJZ110 病因）

| # | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| B1 | Vite 未显式设 `build.target`（默认 es2020 ≈ Chrome 87 基线，输出保留 `?.` 等） | `vite.config.js:31-36`（无 build.target 字段） | WebView < 80 直接 JS 崩 | 显式 `build.target: ['es2020','chrome88']` 并加启动能力探测 |
| B2 | `structuredClone` 4 处（store 状态克隆主链路） | `src/store.jsx:162,181,222,310` | 需要 Chrome 98+；旧 WebView 上**首次 setState 即抛错**，现象为白屏/停在启动图 | 换 `JSON.parse(JSON.stringify())` 或自写 clone（状态本就是纯 JSON），一劳永逸 |
| B3 | `color-mix()` 30 处 / `dvh` 10 处 / `aspect-ratio` 8 处 | `src/styles.css` 全局 | Chrome 111/108/88 以下整条声明失效 → 配色错乱、高度塌陷（不崩但难看） | 启动时 `CSS.supports` 探测，不支持→失败页提示「请升级系统 WebView」，把静默劣化变成明确指引 |
| B4 | `CapacitorHttp` 全局拦截开启 | `capacitor.config.json` plugins.CapacitorHttp.enabled=true | 拦截所有 fetch：FormData/二进制/重定向行为与浏览器不同，WebDAV 同步、AI 上传、主题下载都过这条通道 | 逐一真机验证同步/AI/下载三链路；无必要则关闭（改用原生插件只处理特定请求） |

## 二、全套主题底层模板设计（v2 规范，待实施）

### 设计原则
- **catalog 与 manifest 分离**：`themes.json`（目录，已上线）只放索引；每个主题一个 `themes/<id>/manifest.json` 描述全部资源。
- **只增不改用户数据**：账目类型图标切换走「图标包重定向」（全局设置指向包基地址），不改动 `state.cats[].icon` 的 `girl:` 值，卸载主题即还原。
- **复用现有管线**：壁纸 `media.saveWallpaper`、菜单/发现页图标 `replaceBlob('tab_'+key)` + `settings.tabIconAt` 时间戳，全部已存在。

### manifest schema（schema: 2）

```jsonc
// themes/ocean/manifest.json —— 三个渠道同构可达（cms.js 渠道链）
{
  "id": "ocean",
  "schema": 2,
  "ver": "1.0.0",
  "minApp": "3.7.0",            // 低于此版本的应用忽略新字段
  "name": "深海 · Ocean",
  "author": "...",
  "desc": "...",
  "wallpaper": "wall.jpg",      // 必填：锁屏感主视觉（走 saveWallpaper）
  "palette": {                  // 可选：CSS 变量子集覆盖（只允许白名单变量）
    "brand": "#2b6cb0", "brand2": "#3b82f6", "bg": "#f2f7fb"
  },
  "tabIcons": {                 // 可选：底部菜单四图标（相对 manifest 目录）
    "home": "tab/home.png", "charts": "tab/charts.png",
    "discover": "tab/discover.png", "profile": "tab/profile.png"
  },
  "catIcons": { "pack": "cat/" },  // 可选：整套账目类型图标包（文件名 = girl 键名，如 cat/food.png）
  "discIcons": { "scan": "disc/scan.png" } // 可选：发现页工具图标（键 = DISCOVER_TOOLS.key）
}
```

### 应用 / 卸载 / 同步

| 动作 | 机制 |
|---|---|
| 应用 | fetch manifest → 按字段逐项走现有管线；`palette` 写 `settings.themePalette`（ThemeProvider 注入 CSS 变量）；`catIcons.pack` 写 `settings.catIconPack = <CMS_BASE>/themes/ocean/` |
| 账目类型图标渲染 | `iconRegistry.js` ValueIcon 的 `girl:` 分支加一行：`settings.catIconPack` 存在时 `src = packBase + key + '.png'`，`onError` 回落本地 `./girl/<key>.png`（不增加下载步骤，`<img>` 直显无 CORS 限制） |
| 卸载/还原 | `settings.catIconPack=null` + `tabIconAt`/`discIconAt` 时间戳清空 + 壁纸清除，全部现有 API |
| 同步新主题 | `themes.json` 目录 30s 内存 / 10min 磁盘缓存已内置（cms.js），新主题 push 后商城页自动出现 |

### 安全边界
manifest 字段白名单解析（复用 cms.js 解析器风格）；`catIconPack`/资源路径必须落在 `CMS_BASES` 三源 allowlist 内；`palette` 仅接受白名单 CSS 变量名 + 颜色格式校验（防注入任意 CSS）。

## 三、代码质量审计（屎山 & bug）

### 总体评价
16,824 行源码，**0 TODO / 0 FIXME / 0 console.log / 0 debugger**，测试 478 项、一致性 7 项、CI 全链路——工程纪律在独立开发项目里属第一梯队。屎山风险集中在「单文件过大」而非「混乱」。

### 屎山候选（按行数，建议拆分）

| 文件 | 行数 | 问题 | 建议 |
|---|---|---|---|
| `src/pages/SettingsSections.jsx` | 1398 | 10+ 个设置分组塞一个文件，每加一设置全文件 re-render | 按分组拆 `settings/`（Appearance/Ai/Prefs/Notify/Data 五个文件） |
| `src/iconRegistry.js` | 1078 | 大部分是表数据（可接受），但目录/键集/渲染函数混在一起 | 表数据抽 JSON，逻辑留 ~200 行 |
| `src/utils.js` | 831 | 大杂烩：日期/金额/CSV/脱敏/图像像素判定/深链全在这 | 按域拆 `utils/`（money.ts/csv/mask/image） |
| `src/ai.js` | 757 | 提示词拼装 + 请求 + 缓存 + 风格卡四合一 | 请求层与提示词层分离 |
| `src/update-ctx.jsx` | 622 | 下载状态机复杂（多源+看门狗+续传），但逻辑内聚 | 可接受；补状态机图注释即可 |

### bug 隐患（静态检测命中）

1. **`structuredClone` 4 处**（`store.jsx:162/181/222/310`）：见 B2，基线 Chrome 98+。低版本设备上每次写状态都抛错，且发生在挂载后（失败页拦不到）——**这是「部分用户进不去」的候选真凶**，建议本轮就修。
2. **`CapacitorHttp.enabled=true`**：见 B4，全局 fetch 拦截与 WebDAV/AI/下载三链路的兼容性从未被专项验证过。
3. **CSS 现代特性无降级声明**：`color-mix` 多为唯一声明（无 fallback 行），旧 WebView 上背景直接失效。见 B3。
4. `notice.js` fetch 主源 `raw.githubusercontent.com` 国内不可达时每次公告检查都先等 5s 超时（v3.6.6 已加 gitee 镜像为备源，但主源仍排第一；建议渠道顺序对齐 cms.js：gitee → jsDelivr → github）。

### 亮点（保持）
零依赖启动兜底（内联脚本 + 看门狗 + 自愈按钮）、多源下载 + SHA-256 强校验（实测拦截过镜像污染包）、纯函数全测试化、公告/名单/主题的「push 即发布」体系。
